# gui — 카메라·LiDAR 캘리브레이션 GUI

FAST-Calib의 캘리브레이션 방법은 그대로 두고, 사용 과정을 GUI로 만드는 작업.
알고리즘 원본(`../src`, `../include`)은 참조용으로 두고 건드리지 않는다.

## 실행 환경

새로 설치하려면 저장소 루트의 [`../README.md`](../README.md#2-설치-한-번에)나
`../scripts/setup_env.sh`, `../requirements.txt`를 쓰면 된다. 아래는 이 문서가
쓰인 시점의 개발 머신 상태 기록.

**반드시 `python3.10`을 쓸 것.** 이 머신의 `python3`는 3.8(ROS Noetic)이고
필요한 패키지는 3.10 쪽에 있다.

```bash
python3.10 --version     # 3.10.18
```

필요 패키지는 모두 설치되어 있다:
`PySide6 6.9.3`, `pyqtgraph 0.14.0`, `rosbags 0.11.3`,
`opencv-python 4.11`(ArUco 포함), `open3d 0.19`, `numpy`, `scipy`

ROS는 필요 없다. `rosbags`가 순수 파이썬으로 bag을 읽으므로
`source /opt/ros/...`도, `roscore`도 띄우지 않는다.

시스템 라이브러리 하나가 필요하다 (설치 완료됨):
```bash
sudo apt install -y libxcb-cursor0     # Qt 6.5+ xcb 플러그인
```

## 1단계 사용법

**bag 을 여러 개 넣을 수 있다.** 취득 방식이 두 가지라서다.

- 한 번 길게 켜두고 보드를 들고 여러 자리를 옮겨다닌 경우 → bag 하나
- 자리마다 짧게 끊어 찍은 경우 → bag 여러 개, 각각이 scene 하나
- 둘을 섞어도 된다

절차:

1. `bag 추가…` — 파일 대화상자에서 여러 개를 한 번에 골라도 된다
2. 목록에서 bag 을 클릭하면 그 bag 의 토픽이 아래 표에 나온다
3. 표의 줄을 **더블클릭** 하면 타입에 맞는 칸으로 들어간다.
   `← LiDAR로 지정` / `← 카메라로 지정` 버튼이나 직접 타이핑도 된다 —
   **자동으로 골라주지는 않는다**
4. 둘 다 정하면 왼쪽 1단계에 `✓`

토픽 이름이 일부 bag 에만 있으면 어느 bag 이 문제인지 빨간 글씨로 알려준다.
`보조 토픽 숨기기`를 끄면 `/status`, `parameter_*`, `rosout` 까지 다 보인다.

scene 이 캡처된 bag 은 제거되지 않는다.

## 2단계 사용법 — 카메라

**보통은 맨 위 `저장된 카메라`에서 고르면 끝난다.** 목록은
`gui/config/camera_intrinsics.yaml`에서 읽는다 — 코드가 아니라 데이터 파일이므로
카메라가 늘어나도 파일만 고치면 되고, 저장소에 있으니 다른 머신에서도 같은 목록이 보인다.

값을 직접 고치면 드롭다운이 `— 직접 입력 —`으로 바뀐다.
새 카메라라면 값을 넣고 `현재 값을 저장…`을 누르면 목록에 추가된다.
이름을 물어보는데, **기존 이름을 쓰면 덮어쓴다** — 그 경우 한 번 더 확인한다.

처음 보는 카메라는 `붙여넣기로 입력…`에 리그의 캘리브레이션 파일 형식을 그대로 넣으면 아홉 칸이 채워진다.

```
cameraMatrix: "909.02985013, 0.0, 937.59143638, 0.0, 908.78643070, 779.38051307, 0.0, 0.0, 1.0"
distCoeffs: "-0.25862002, 0.05286346, -0.00163891, 0.00090263, -0.00409366"
```

`bag에서 프레임 불러오기` → `왜곡 보정 적용`으로 **직선이 직선으로 펴지는지** 확인한다.
문틀·천장 빔·바닥 이음선이 판단하기 좋다. 이게 이 단계의 핵심이다 —
숫자가 이 카메라의 것이 맞는지 확인할 방법은 이것뿐이다.

**k3를 반드시 넣을 것.** FAST-Calib 원본은 다섯 번째 왜곡 계수를 0으로 강제하는데,
이 리그의 두 카메라 모두 k3가 0이 아니라서 그대로 두면 광각 가장자리에 계통 오차가 남는다.

## 3단계 사용법 — 타겟

**보통은 맨 위 `저장된 보드`에서 고르면 끝난다.** 목록은
`gui/config/target_specs.yaml` 에서 읽는다. 기본으로 두 개가 들어 있다.

| 이름 | 내용 |
|---|---|
| 원본 CAD | FAST-Calib 기본 도면 |
| 데모 보드 (0.594배) | 지금 쓰는 축소 출력본. 마커 118.8mm, 구멍 지름 142.6mm |

여섯 개 치수를 넣으면 오른쪽에 **보드가 실척으로 그려진다.** 마커에는 ArUco ID가 표시된다.
값을 직접 고치면 드롭다운이 `— 직접 입력 —` 으로 바뀌고,
`현재 값을 저장…` 으로 목록에 추가할 수 있다 (같은 이름이면 확인 후 덮어쓴다).

원본 CAD를 비율로 축소·확대해 출력했다면 배율만 넣고 `원본 CAD × 배율 적용`을 누르면 된다.
(예: `0.594` → 마커 118.8mm, 구멍 지름 142.56mm)

좌우 마커 겹침, 구멍 겹침, 구멍이 마커를 침범하는 경우를 자동으로 잡아 경고한다.

여기가 틀리면 **뒤에서 잡아낼 방법이 없다.** 보드 모델이 일관되게 틀리면
재투영 오차는 작게 유지되면서 pose만 편향되기 때문이다. 도면을 실물과 줄자로 대조할 것.

## 4단계 사용법 — Scene 캡처

**bag을 자르지 않는다.** 타임라인을 훑고, 남길 시점을 (bag, 타임스탬프)로 기록할 뿐이다.

bag 이 여러 개면 위쪽에 선택 콤보가 나온다. bag 을 바꿔가며 각각에서 한 장씩 캡처하면
"자리마다 짧게 끊어 찍은" 데이터가 그대로 처리된다.

| 조작 | 동작 |
|---|---|
| 위쪽 콤보 | bag 전환 (여러 개일 때만 보임) |
| 슬라이더 드래그 / `←` `→` | 프레임 이동 |
| `Space` 또는 `이 시점 캡처` | 현재 시점을 scene으로 기록 |
| `scene 자동 추천…` | 녹화 전체를 훑어 후보를 제시 (추가는 확인 후) |
| `선택 삭제` | 캡처한 scene 제거 |

자동 추천이 훑고 나면 타임라인 아래 띠에 마커가 보인 구간이 칠해진다.
초록 = 마커 4개, 노랑 = 1~3개, 회색 = 없음. 검은 눈금은 추천이 고른 시점.

별도의 `타임라인 스캔` 버튼이 있었는데 없앴다 — 내놓는 게 띠뿐이라,
정작 일하는 버튼을 누르기 전에 눌러야 하는 버튼이었다.

현재 프레임 패널에 그때그때 나오는 값:

- **마커** — 4개가 아니면 캡처 버튼이 잠긴다
- **마커 크기** — 40px 미만이면 경고. ArUco 6x6은 테두리 포함 8x8 셀이라
  30px면 셀당 3.7px 뿐이고, 코너 서브픽셀 정밀도가 무너진다. 보드를 가까이 놓아야 한다
- **거리**
- **기울기** — 12° 미만이면 경고. 평면 타겟을 정면에서 보면 PnP가 불량조건이 되어
  보드 법선과 깊이가 흔들린다. 20~40° 기울여 잡는 게 좋다
- **재투영** — 1.5px 넘으면 경고

디코딩과 검출은 별도 스레드에서 돌고, 슬라이더를 끌면 마지막 요청만 처리한다.

## 5단계 사용법 — 거리 필터

scene 을 고르면 그 시각 ±0.5초의 LiDAR 를 누적해 3D 뷰에 띄운다.
회전형 센서라도 스윕마다 지터가 있어 누적하면 표면이 실제로 더 촘촘해진다 —
같은 데이터에서 1 스윕은 검출 실패, 5 스윕부터 안정, 8 스윕 이후로는 나아지지 않았다.

처음에는 박스가 클라우드 전체 범위로 잡혀 있으니, 숫자를 줄여가며 보드만 남기면 된다.

- 스핀박스는 정밀 조정, 슬라이더는 빠른 탐색. 둘은 서로 동기화된다
- 노란 점은 검출 지점, 자홍색 큰 점은 맞춘 원의 중심
- `다른 scene에 복사` — 센서가 고정이고 보드만 옮겼다면 시작점으로 쓸 만하다

**색상 (Color Transformer)** — rviz 와 같은 구성

| 기준 | 쓰임 |
|---|---|
| Intensity (기본) | 캘판은 흰 판에 검은 마커라 반사 강도 차이가 커서 판을 찾기 가장 쉽다 |
| 축 (AxisColor) | x/y/z 중 하나. 지면과 수직 물체를 가르기 좋다 |
| 거리 | 원점으로부터의 거리 |
| 단색 | 예전 방식 |

컬러맵 5종(turbo / viridis / grey / hot / rainbow), `반전`, 그리고 값 범위 설정이 있다.
`자동 범위` 를 끄면 min/max 를 직접 넣을 수 있다 — 특정 구간만 색을 몰아주면
대비가 살아나서 판이 더 잘 보인다. 자동일 때는 1~99 분위수를 쓰므로
멀리 튄 점 몇 개 때문에 색이 뭉개지지 않는다.

`박스 밖 숨기기` 를 켜면 필터 박스 안만 남는다. 꺼두면 밖은 흐리게 표시된다.
intensity 필드가 없는 토픽이면 그렇다고 알려준다.

**화면 조작**

| | |
|---|---|
| 좌드래그 / 휠 / 중클릭 | 회전 / 확대 / 이동 |
| `Top` `Front` `Side` `Iso` | 보는 각도만 바꾼다. 위치와 거리는 그대로 |
| `박스에 맞춤` | 필터 박스를 화면에 채우고 **회전 중심을 박스 안으로** 옮긴다 |
| `전체 보기` | 클라우드 전체를 다시 본다 |

휠 확대는 **커서 아래 점을 향해** 들어간다. 회전 중심이 따라오므로 아무리 확대해도
막히지 않고, 확대한 자리에서 회전과 이동이 그대로 먹는다.
(회전 중심을 고정해두면 rviz Orbit 처럼 일정 이상 못 들어가고 근처에서 이동도 안 된다.)

넓은 실외 클라우드는 처음 열 때 회전 중심이 수십 미터 밖에 잡힌다.
박스를 대충 보드 근처로 좁힌 뒤 `박스에 맞춤` 을 누르면 바로 작업할 수 있는 시점이 된다.

### 검출 방식

| 방식 | 원리 | ring |
|---|---|---|
| **FAST-Calib (기계식, 링 점프)** (기본) | 링을 따라가다 거리가 튀는 곳을 찾고, RANSAC 으로 원을 찾아 그 점을 지우며 반복 | 필요 |
| FAST-Calib (솔리드, 이웃 각도) | 각 점의 이웃이 한쪽으로 비었는지 본다. Livox 같은 솔리드스테이트용 | 불필요 |
| 링 점프 쌍 묶기 | 위 기계식의 변형. 구멍 좌우 테두리를 한 쌍으로 묶는다 | 필요 |
| 평면 격자 | 평면을 격자로 만들어 윤곽을 채우고, 남은 빈 곳을 구멍으로 본다 | 불필요 |
| 실험용 | 평면 격자의 사본. 손대는 쪽은 이쪽이다 | 불필요 |

앞의 둘은 원본 이식이고 뒤의 셋은 여기서 쓴 것이다.

**실험용이 따로 있는 이유.** 이 리그에서 실제로 쓰는 것은 평면 격자다 — 차량 시스템이
`merge` 토픽을 쓰고 거기엔 `ring` 이 없어 링 기반 두 방식이 아예 못 돌고, 솔리드
방식은 검출이 전멸한다. 그래서 평면 격자는 손댈 곳이 아니다. 대신 사본을 두고 그쪽을
고친다. 같은 scene 에서 둘을 번갈아 눌러 비교하면 바뀐 것이 나은지 바로 보인다.
처음에는 두 방식의 결과가 완전히 같다 (18 scene 에서 중심 차이 0).

여러 LiDAR 를 정합한 클라우드에는 `ring` 이 남지 않아 기계식 방식을 쓸 수 없다.
그때 솔리드 방식으로 넘어가면 점 간격과 구멍 크기 사이에 검색 반경이 놓여야 한다는
제약에 걸린다 — 11m 취득(간격 20mm, 구멍 반지름 71mm)에서는 그 창이 닫혀 평면의 38%가
경계로 찍히고 검출이 전멸했다. **평면 격자가 그 경우를 위해 있다.**

### 동작 범위

두 가지로 잰다. **실측**은 정지한 보드를 연속 10스윕 찍어 같은 ROI 로 돌린 것이고
(test_3/1.bag), **합성**은 `gui/core/synth.py` 가 광선 추적으로 만든 96개 조건이다
— 센서 해상도 4종 × 잡음 2종 × 거리 4종 × 자세 3종.

| 방식 | 실측 10스윕 | 합성 96조건 | 중심 오차 (최대) |
|---|---|---|---|
| FAST-Calib 기계식 | **10/10** | 70% | 4.0 mm (42.2) |
| 평면 격자 | **10/10** | 30% | **1.4 mm (4.5)** |
| 링 점프 쌍 묶기 | 2/10 | 40% | 7.6 mm (92.4) |
| FAST-Calib 솔리드 | 0/10 | 22% | 19.0 mm (102.7) |

**검출률과 정확도가 서로 다른 것을 말한다.** 기계식은 네 개를 가장 자주 찾지만
크게 틀릴 수 있다 — 최대 오차가 한 자릿수 더 크다. 테두리 점이 중심을 둘러싸지 않아도
원으로 인정하기 때문이다. 격자는 반대로, 더 자주 포기하지만 답을 내면 거의 맞는다.

솔리드 방식의 0/10 은 성능이 아니라 **용도가 다른 것**이다. 이 리그는 기계식 LiDAR 다.

합성에서 격자가 낮은 이유는 아직 규명 중이다. 실패가 조건이 아니라 특정 자세
(보드가 정면에 가까울 때)에 몰려 있다.

재측정은 이렇게 한다.

```bash
python3.10 gui/check_synth.py                       # 96조건 회귀
python3.10 gui/check_synth.py --detail              # 조건별 표
python3.10 gui/check_synth.py --sweep 항목=값,값,값   # 임계값의 고원 찾기
```

> **주의** — 이 문서와 코드 주석에 남은 다른 측정치 중 일부는 생성기가 두 군데 틀린
> 상태에서 잰 것이다. 빔이 구멍을 통과하는 조건이 반대였고, 패널이 자기 구멍 배치보다
> 작아 구멍이 보드 가장자리를 뚫고 나갔다. 둘 다 고쳤지만 **그 이전 숫자는 재측정 전까지
> 믿을 수 없다.** 논지(어느 값이 고원 중앙인지, 어떤 임계값이 어느 크기 위에서는
> 무의미해지는지)는 그대로다.

### 박스는 좁게

임계값보다 **필터 박스 크기가 결과를 더 크게 좌우한다.** 여유를 120 mm 에서 700 mm 로
넓히자 검출률이 가파르게 떨어졌다 (보드 뒤 0.3~1 m 에 벽, 기울기 15~50도인 조건).
이 숫자들도 생성기 수정 전 것이라 절대값은 재측정이 필요하지만, 경향은 분명하고
박스에 회전을 넣은 이유이기도 하다.

구멍을 통과한 광선은 뒤에 있는 것에 맞는다. 벽이나 보드를 든 사람이 가까이 있으면
그 점들이 보드 평면 허용치 안에 들어와 **구멍을 메운다.** 임계값을 아무리 조정해도
회복되지 않으므로, 박스를 보드에 바짝 붙이는 게 유일한 해법이다.

### 관측 반지름은 도면과 다르다

구멍은 도면보다 **항상 크게** 읽힌다. 두 가지가 거리에 비례해 반지름을 밀어낸다.

- **빔 폭** — 빔은 점이 아니라 3 m 에서 지름 10 mm 인 원반이다. 중심이 아직 판 위에 있어도
  가장자리가 구멍에 걸치면 돌아오는 빛이 모자라 기록되지 않고, 걸친 테두리는 면이 아니라
  벽이라 반사가 옆으로 튄다. 살아남는 마지막 반환점이 실제 테두리보다 빔 반지름만큼 밖이다
- **샘플링** — 그 바깥으로 다시 최대 한 점 간격까지 벌어지고, 피팅은 그 점들을 따른다

```
예상 반지름 = 도면 + 빔 반지름 + 점 간격 / 2
```

3.2 m 에서 71.3 + 4.8 + 3.9 = **80.0 mm**, 실측과 맞는다.

> 이 부호는 원래 반대였다. "빔이 구멍에 완전히 들어가야 통과한다"고 보고 빔 반지름을
> **뺐다.** 예측 69.5 mm 대 실측 80 mm 로 어긋났고, 매 스윕 구멍 하나가 반지름 검사에서
> 탈락해 3/4 에서 멈췄다. 이걸 못 잡은 이유는 `synth.py` 가 같은 가정으로 광선을 쐈기
> 때문이다 — **생성기가 검증 대상인 전제를 스스로 깔고 있어서** 합성에서는 반지름이
> 정확히 나오고 실제에서만 틀렸다. 순환은 안에서 보이지 않는다.
> 줄자로 구멍을 재보니 142 mm(도면 142.6 mm)였고, 검출기 셋은 모두 160 mm 를 말하고
> 있었다. **실물 측정 하나가 끊었다.**

그래서 허용 범위를 비율로 찍지 않고 **거리에서 계산한다.** 도면 71 mm 인 구멍이
3 m 에서 80 mm 로 보이는 것은 정상이다.

다만 실측은 84~87 mm 로 모델보다 아직 4~7 mm 크다. 허용 범위 안이라 검출은 되지만
모델이 전부를 설명하지는 못한다.

### 결과 읽는 법

`원 검출` 을 누르면 왼쪽 아래에 나온다. 방식에 따라 항목이 다르다.

| 항목 | 읽는 법 |
|---|---|
| 점 간격 (단일 스윕) | 누적 전 한 스윕 기준. 40mm 넘으면 경고 |
| 격자 셀 | 점 간격에서 자동으로 정해진다 (점유 격자) |
| 구멍 후보 | 격자에서 찾은 빈 영역 수. 4개 미만이면 박스에 보드 전체가 안 들어온 것 (점유 격자) |
| 경계 검출 반경 / 경계점 / 클러스터 | 경계점 클러스터 방식일 때만 |
| 평면 잔차 | 20mm 넘으면 잡힌 평면이 보드가 아닐 수 있다 |
| 원 검출 | **4/4 가 목표.** 초록이 되면 그 scene 은 끝 |
| 맞춘 원 | 반지름이 도면보다 큰 것은 정상이다 (위 절 참고). 다만 **기계식 방식에서는 반지름이 크게 틀리면 중심도 틀렸다** — 합성에서 상관 0.83 이었고, 반지름 오차 5 mm 이상인 경우 중심 오차가 25.7 mm 로 정상(4.4 mm)의 여섯 배였다. 격자·링 방식은 그 상관이 거의 없다 |

**박스는 보드에 바짝 붙일 것.** 속도 때문만이 아니다 — 구멍 뒤 벽까지 박스에 들어오면
그 점들이 구멍을 메워서 검출이 실패한다. 보드 바깥 여유 **10~30cm** 가 적당하다. 40만 점을 넘으면 몇 초 걸릴
수 있다고 한 번 확인을 받는다 — 진행해도 되고, 좁혀도 된다.

숫자를 끌고 있는 동안에는 박스와 색만 즉시 갱신되고, 검출은 `원 검출` 을 누를 때만 돈다.
여섯 값을 다 정하기 전에는 중간 결과가 의미 없기 때문이다.

간격 경고가 계속 뜨면 박스를 아무리 만져도 소용없다. 보드를 가까이 놓고 다시 찍어야 한다.

## 6단계 사용법 — 캘리브레이션

`모든 scene 검출 후 계산` 을 누르면 캡처한 scene 마다 카메라·LiDAR 검출을 돌리고,
성공한 것들에 하나의 extrinsic 을 맞춘다.

표의 체크박스로 scene 을 넣고 빼면 **즉시 다시 계산된다.**
(원본은 로그 파일의 마지막 세 항목을 무조건 쓴다. 개수 제한도 선택권도 없다.)

| 열 | 읽는 법 |
|---|---|
| RMSE | 그 scene 의 네 쌍이 얼마나 맞는지 |
| 제외 시 변화 | **그 scene 을 빼면 답이 얼마나 움직이는지.** 30mm 나 0.5° 를 넘으면 빨갛게 표시된다 |
| 비고 | 검출이 실패했다면 그 이유 |

`제외 시 변화` 가 중요하다. 조용히 틀린 scene 은 자기 RMSE 는 낮게 유지하면서
extrinsic 을 엉뚱한 데로 끌고 가므로, 잔차만 봐서는 안 잡힌다.

**커버리지** 막대는 보드가 실제로 얼마나 움직였는지를 보여준다.
같은 자리에서 여러 번 찍은 scene 은 점만 늘릴 뿐 정보를 더하지 않는다.
가로·세로 2m, 높이 1m, 기울기 30° 정도 퍼지면 충분하다.

합성 데이터로 잰 scene 수별 정확도 (LiDAR 노이즈 3mm, 카메라 1mm):

| scene 수 | 회전 오차 | 병진 오차 |
|---|---|---|
| 1 | 0.55° | 23 mm |
| 3 | 0.16° | 7.6 mm |
| 6 | 0.04° | 2.7 mm |

scene 이 3개 미만이면 경고가 뜬다. 구멍 네 개가 이루는 사각형은 180° 돌려도
똑같아 보여서, scene 하나만으로는 보드 방향이 뒤집힌 해와 구별되지 않는다.

## 프로젝트 저장

`프로젝트 → 저장` (Ctrl+S) 하면 파일이 **두 개** 생긴다.

```
내프로젝트.calib.yaml     토픽, 카메라, 타겟, scene 목록 — 수 KB. 공유·동기화용
내프로젝트.local.yaml     이 머신에서의 bag 경로 목록 — 머신마다 다르므로 분리
```

scene 은 bag 을 **파일 이름**으로 기억한다. 다른 컴퓨터에서는 `.calib.yaml` 만 가져가서
같은 이름의 bag 들을 다시 추가하면 scene·필터·설정이 그대로 이어진다.

# 진단 도구

본체와 별개로, 환경과 데이터를 빠르게 확인하는 스크립트들.

## `gui/check_gl.py` — 3D 뷰 확인

OpenGL이 제대로 도는지, 포인트클라우드 렌더링이 쓸 만한지 확인한다.
실데이터 없이 합성 장면(지면 + 벽 + 구멍 4개 뚫린 보드, 40만 점)을 띄운다.

```bash
python3.10 gui/check_gl.py
```

**보는 법**
- `Top` `Front` `Side` `Iso` 버튼 — 시점 프리셋
- `Fit` — 데이터에 맞춰 카메라 맞춤
- 마우스: 좌드래그 회전 / 휠 줌 / 중클릭 팬 (rviz와 동일)
- `필터 하이라이트` 체크 — 박스 안(파랑) / 밖(회색). 나중에 distance filter 화면이 될 표현
- 상태바에 FPS와 GL 렌더러가 뜬다. `llvmpipe`면 소프트웨어 렌더링이라 문제.

이 머신 결과: `NVIDIA GeForce RTX 4070`, 60 FPS(vsync 상한) — 정상.

## `gui/check_bag.py` — bag에 뭐가 들어있나

토픽 목록, 타입, 개수, 주파수를 뽑는다. 인덱스만 읽어서 큰 bag도 빠르다.

```bash
python3.10 gui/check_bag.py <bag 경로> [bag2 ...]
```

예:
```bash
python3.10 gui/check_bag.py /mnt/ssd990/bag_fast-calib/fast_calib_2026-08-04-10-41-32.bag
```

출력 끝에 `LiDAR 후보` / `이미지 후보`가 나온다. 이건 **타입으로 거른 목록일 뿐**
자동 선택이 아니다 — 어느 걸 쓸지는 사람이 정한다.

토픽이 많아 지저분하면 걸러서 보면 된다:
```bash
python3.10 gui/check_bag.py <bag> | grep -Ev "parameter_|/status|rosout|diagnostics"
```

## `gui/check_frame.py` — 프레임 하나 꺼내보기

지정한 시점의 LiDAR 한 장과 이미지 한 장을 디코딩해서,
클라우드 필드 구성 / 점 개수 / 거리 범위 / 처리 시간 / ArUco 검출 여부를 보고한다.

```bash
python3.10 gui/check_frame.py <bag> --lidar <토픽> --camera <토픽> [--at 0.5] [--show]
```

- `--at` : 녹화 구간에서의 위치 (0.0=시작, 0.5=중간, 1.0=끝)
- `--show` : 3D 뷰로 클라우드를 띄운다
- `--outdir` : 이미지 저장 위치 (기본 `/tmp`, `frame.png`로 저장)

예:
```bash
python3.10 gui/check_frame.py \
  /mnt/ssd990/bag_fast-calib/fast_calib_2026-08-04-10-41-32.bag \
  --lidar /sensor/lidar/merge/no_ground_points \
  --camera /sensor/camera/top_center/compressed \
  --at 0.5 --show
```

**확인할 것**
- `ring 필드 있음/없음` — 없으면 기계식 경로(`detect_mech_lidar`)를 못 쓴다
- `ArUco 검출` — 0개면 그 시점에 보드가 안 보이거나 너무 작은 것
- `한 프레임 합계` — 스크러버 반응성의 상한
